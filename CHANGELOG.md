# Changelog

## 0.37.0

### Added: сырое тело входящего вебхука в trace-логе (`-vvv`)

- `/api/v1/grafana`, `/api/v1/alertmanager` и `/api/v1/gitlab` читают тело
  целиком и пишут его на уровне V3 как `grafana: raw payload:` (и так же для
  остальных двух), после чего декодируют JSON из прочитанных байт. Раньше в логе
  было только отрендеренное сообщение, и разобрать, что именно прислала Grafana
  с `message_source: webhook`, было нечем.
- Тело логируется и тогда, когда JSON невалиден: запись идёт до декодирования.
- Лог ограничен 64 KiB; более длинное тело пишется усечённым с пометкой
  `(truncated to 65536 of N bytes)`. На само сообщение усечение не влияет.
- Заголовки не логируются: в них ключи авторизации.
- Коды и тела ответов не изменились.

### Added: точечный трейс payload по запросу — `?trace=1` / `X-Botx-Trace`

- Маркер на запросе кладёт в лог тело и отрендеренное сообщение независимо от
  verbosity, поэтому ради одного алерта раз в сутки больше не нужно поднимать
  `-vvv` на весь поток. Ставится правкой URL у отправителя, рестарт шлюзу не
  нужен, конфиг не меняется.
- Включают `?trace`, `?trace=`, `?trace=1|true|yes|on` (регистр не важен) и
  заголовок `X-Botx-Trace` с теми же значениями. Параметр главнее заголовка:
  `?trace=0` гасит `X-Botx-Trace: 1`. Неизвестное значение не включает трейс и
  не ломает запрос.
- `?trace=0` снимает только принудительный режим: при `-vvv` тело по-прежнему
  пишется на V3. При `-vvv` вместе с маркером запись всё равно одна.
- В записи появилась скобка с пометками: `id=` (тот же `request_id`, что в
  access-логе, для связи записи с HTTP-строкой), `request_trace=true` у
  принудительных записей и отметка усечения.
- Тело неаутентифицированного запроса не читается и не логируется.
- Лог 64 KiB теперь ограничивает и отрендеренное сообщение, а не только тело.
- Недочитанное тело (обрыв соединения, `Content-Length` больше фактических
  байт) даёт `400 cannot read request body` и не пишется в лог: в записи
  попадает только полностью прочитанный пейлоад.
- Маркер требует разрешения `server.allow_request_trace: true`, **по умолчанию
  `false`**. Без разрешения он игнорируется молча: доставка не ломается, ошибки
  клиент не получает, `request_trace=true` в логе не появляется. Разрешение
  читается на старте и стоит рестарта один раз, дальше отправитель включает и
  выключает трейс правкой своего URL. На `-vvv` настройка не влияет: тело
  пишется на V3 независимо от неё.

## 0.36.0

### Added: скоуп api-ключа — изоляция команд на `/send`, `/alertmanager`, `/grafana`

- У ключа в `server.api_keys` появился белый список `chats`; запрос в чат вне
  списка отклоняется с `403 chat not allowed for this key`.
- Проверяется финальный адресат, после резолва алиаса и подстановки
  `default_chat_id`, поэтому обойти скоуп голым UUID нельзя.
- Скоупленному ключу `GET /chats/alias/list` показывает только его чаты, а чужой
  и несуществующий чат отвечают одинаково.
- Ключ без `chats` не ограничен: прежние конфиги работают как раньше.

### Added: `message_source` для Grafana — текст сообщения рендерит Grafana

- `server.grafana.message_source: webhook` отправляет в чат `title` и `message`,
  которые Grafana уже отрендерила своим notification template, вместо того чтобы
  собирать текст встроенным шаблоном шлюза. Формат настраивается в Grafana
  по contact point'у, без правки конфига express-botx и без релиза.
- Пустой `message` в пейлоаде откатывает рендер на шаблон шлюза; вебхуки
  Alertmanager поля не содержат, на `/api/v1/alertmanager` настройка не влияет.
- По умолчанию `template` — прежнее поведение сохранено.

## 0.35.0

### Added: HTTPS/TLS serving с hot reload сертификата

- `serve` и `serve --enqueue` поддерживают opt-in HTTPS через YAML, env или
  `--tls-cert`/`--tls-key`; минимальная версия — TLS 1.2.
- Сертификат и ключ перечитываются по content hash без остановки listener; ошибка
  ротации не сбрасывает последнюю корректную пару.
- Helm умеет создать cert-manager Certificate или смонтировать существующий TLS
  Secret, переключает probes/backend port name на HTTPS и сохраняет прежний HTTP
  render при `tls.enabled=false`.

## 0.34.0

### ⚠️ Breaking: GitLab-конфигурация только через senders

`server.gitlab` теперь содержит только непустой `senders`. Каждый sender
владеет своими `name`, `secret`, `chats`, `events`, `error_events`, `templates`,
`template_files` и `routes`. Для доставки без routes используйте `chats`, а
для fallback при роутинге — явный последний `match: {}`.

`?chat_id=` обходит routes, но остаётся в скоупе sender'а; `?bot=` всегда
игнорируется. Запрос `?chat_id=` на чат вне скоупа — или на in-scope чат,
названный алиасом с bot binding, отличным от цели сендера, — возвращает `403`.
Все «проглоченные» события возвращают `200` с полем `reason`: `event filtered`,
`empty message` или `no route matched`.

`config validate` оффлайн зеркалит проверки старта `serve` для gitlab: алиас без
`id`, две цели в один UUID, `route[].chats` вне скоупа и конфликт bot binding —
ошибки; raw UUID / алиас без `bot` в multi-bot — предупреждения. Старт `serve`
отвергает те же конфигурации.

### ⚠️ Breaking: единый формат ответа (`MultiSendResponse`) на всех точках отправки

Все эндпоинты отправки (`/send`, `/alertmanager`, `/grafana`, `/gitlab`) и CLI
(`send`, `enqueue`) теперь возвращают **единый конверт** `MultiSendResponse` —
даже для одного чата:

```json
{"ok": true,
 "results": [{"chat": "a", "sync_id": "..."},
             {"chat": "b", "request_id": "...", "queued": true}],
 "errors":  [{"chat": "c", "error": "resolving chat: ..."}]}
```

Раньше `/send`/`/alertmanager`/`/grafana` отвечали `{"ok":true,"sync_id":"..."}`,
а `/gitlab` — то одиночной, то fan-out-формой. Клиентам, которым нужен прежний
контракт, следует остаться на версии `0.33.x`.

### Added: multi-chat fan-out (`chat_id` через запятую)

- `chat_id=a,b,c` (в теле `/send` или `?chat_id=a,b,c` у вебхуков и CLI)
  рассылает сообщение во **все** перечисленные чаты (fan-out, best-effort).
  Дубликаты схлопываются, порядок сохраняется, чат и бот резолвятся для каждого
  таргета отдельно; в `/send` inline-mentions парсятся резолвером каждого бота.
- **Коды ответа:** `200` — sync (доставлено ≥1 чата), `202` — async (enqueue),
  `502` — во все чаты не удалось. Request-level ошибки (битый JSON, пустой
  `chat_id`, невалидный `status`, неподдерживаемый media-type) сохраняют прежнюю
  форму `{"ok":false,"error":"..."}` с кодами `400`/`415`.
- **Async expand:** в режиме `serve --enqueue` (и в CLI `enqueue`) многочатовый
  `chat_id` раскрывается в N независимых сообщений в очереди (по одному на чат)
  для per-chat retry/ack без дублей; worker не изменён.

См. [docs/integrations.md](docs/integrations.md#мульти-чат-и-единый-ответ-multisendresponse).
